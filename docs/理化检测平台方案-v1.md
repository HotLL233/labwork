# 理化检测平台方案 v1

日期：2026-10-09。依据：桌面“理化报告”中的 12 个快捷方式及其目标工作簿、GitHub 公开仓库。

已确认：实验室内网多人协作，Microsoft Excel 和 WPS 都会使用。核心需求：在平台直接录入、计算，并写入现有 Excel 表格。

## 1. 推荐方案

建立一个中文网页平台，统一管理项目、样品、检测原始记录、计算方法与试剂标定参数。人员从浏览器录入，平台完成计算和校验，随后将原始数据及结果写回对应的现有 Excel 文件、工作表和记录行。

推荐采用 **Django 单体应用 + PostgreSQL + 一个串行 Excel 回写进程**。参考 SENAITE 的检测业务模型，复用 Django 已有的账号、权限、表单、数据库事务和管理后台。首期采用普通网页表格和表单，不拆前后端，不引入微服务、Redis、Celery 或通用工作流引擎。

数据库保存平台业务记录及其版本；现有 Excel 保留为兼容原工作方式的同步台账。不能让数据库与 Excel 同时成为可自由修改的两套主记录。纳管后的数据区域优先通过平台编辑，Excel 手工修改则进入冲突处理。

GitHub 有类似项目，但本次调研没有找到已证实能够直接承接这 12 份现有工作簿、完整保留原表对象并支持可靠回写的现成系统。无论采用哪种框架，都需要完成表格映射、计算核定和回写适配。

### 2.2 应迁移的业务能力

## 3. 不能直接照搬的细节

### 3.1 试剂标注和公式参数有差异

下列是需要业务核定的具体实例，不能据此直接认定历史结果错误，也不能自动选择其中一个浓度：

| 来源位置 | 已读到的差异 | 平台处理要求 |
| --- | --- | --- |
| A3 / 过氧化氢 / H2 与 E3 | 表头浓度 `0.01618 mol/L`，公式系数 `0.01971` | 核定是否为模板示例、旧标定或未同步参数 |
| K001 / 氯离子 / H2 与 E3 | 表头浓度 `0.1033 mol/L`，示例公式系数 `0.1029` | 历史参数保留，核定后建立方法和标定版本 |
| J001 / 水合肼 / H2 与 E3:E5 | 表头浓度 `0.1020 mol/L`，公式系数 `0.104` | 不用当前表头浓度追溯改算历史记录 |
| A3 / 氢离子 / E4:E6 | 保存了 3 个 `#DIV/0!` 缓存错误 | 标记待核查；质量缺失或为零时阻止新计算，不输出 0 冒充结果 |

“例”行用于展示算法，不能导入为真实样品记录。示例参数也不一定代表后续每条检测采用的实际参数。

### 3.2 同名检测项不等于同一方法

- Q 的“氟离子 ”表包含两次称量和两次稀释，结果同时以 ppm 和 % 表示。
- EF 的“氟离子”表包含加标值与仪器示数扣减，字段位置也不同。
- A3 的“氟离子”表是检测完成批号和备注的登记表，不能套用上述计算。
- EF 的二氟乙酸钠方法有温度修正；不能用普通滴定公式覆盖。
- 干燥失重使用 mg；多种滴定使用 g。ppm 与 % 之间的换算还须确认质量浓度/质量分数定义，不能把所有 mg/L 都直接除以 10000 当成百分数。

应按“项目 + 检测项 + 方法版本 + 模板版本”建立映射。月份是查询条件和文件路由条件，不是在系统中继续复制一套业务表。

## 4. 核心操作：平台录入后写回原表

### 4.1 使用流程

1. 登录内网平台，选择项目、样品和检测项。
2. 平台加载已核定方法，显示输入字段、单位、试剂标定参数及预计写入的目标文件和工作表。
3. 录入质量、体积、温度、稀释信息，或直接录入仪器结果；支持同一记录的多次平行测定。
4. 平台自动计算，展示每次结果、换算结果和所用参数；缺少必要输入时显示具体缺项。
5. 可保存草稿。点击“提交并写表”后，平台先提交数据和回写任务，再由后台写入对应 Excel。
6. 页面分别显示数据状态与同步状态：草稿/已提交，以及待回写/回写中/成功/文件占用/冲突/失败。提供重试和源文件定位。
7. 后续复核和修订均留记录。首期是否需“复核通过才写入”，由实验室确定；默认有效提交即可同步，正式报告发布以后再单独管控。

**“平台已保存”不代表“原 Excel 已写入”。** 回写状态必须可查，不因文件被占用而丢失人员已录入的数据。

### 4.2 写入映射实例

以 D006 的“总氮”为例，新记录通常映射到 A 列检测日期、B 列批号、C 列称量质量、D 列滴定体积、E 列结果。实际应用要避开第 1–2 行表头和第 3 行“例”，使用核定后的参数生成对应结果及公式。

以 Q 的“氟离子 ”为例，C–F 列分别对应两次称量/稀释质量，G 列对应仪器示数，H/I 列分别对应 ppm/% 结果；工作表名末尾空格在文件定位时必须保留。平台显示名可以规范化，底层映射不能擅自改原名。

映射最少保存：实际路径、原工作表名、表头特征、字段到列的对应、输入单位、结果字段、示例行、有效数据范围、记录行组规则和模板版本。新增记录从实际记录区确定位置，不能只按工作表最大行号追加，避免跳过预留空行或误占备注区域。

### 4.3 保留原表布局与对象

要求保留工作表顺序、字体、边框、列宽、合并单元格、目录链接、返回目录按钮、条件格式、打印设置及未纳管区域。新行沿用经过确认的记录行样式，所有平行行一起分配。

读写库只是实现手段，不能把“成功保存 xlsx”当成兼容性验收。目前工作簿包含形状按钮及共享公式，直接使用某些读写库整本保存可能损失对象或公式缓存。

推荐先验证 **对 XLSX 压缩包中的目标工作表 XML 作局部更新，其他文件部件保持原样** 的回写方式。采用 Python 标准库 `zipfile` 与 XML 工具即可完成针对现有模板的定点写入；首期限定支持已核定模板，不做任意 Excel 编辑器。只有经过副本兼容性验证的库才能替代该方式。

平台计算已纳管方法的输出，不依赖人员打开 Excel 后才得到结果。向 Excel 结果格写入对应公式及缓存值；已纳管的联动结果一并更新。尚未支持的公式依赖必须阻止该模板上线，不把旧缓存当成新结果。对原有共享公式须保留已有关系，新增结果行采用独立公式，不能无检查地复制共享索引。

实验室已确认同时使用 WPS 和 Microsoft Excel。两种软件中的打开、重算与保存行为都需用副本实测；不能以 Python 文件保存成功代替这一步。

### 4.4 多人协作、占用和恢复

- 一次数据库事务保存提交记录与回写任务，防止“数据有了但写表任务丢了”。同一次提交有唯一任务标识，重复点击或重试不能重复追加。
- 首期一个串行进程处理 12 个文件的回写。同一文件不会由两名平台用户同时修改；队列等待显著影响使用时再改为按文件并行。
- 写前验证路径、模板版本、源文件内容指纹和记录映射。平台自身回写产生的变化按已完成任务版本链重新定位；外部修改则停止本次写入，显示待核查。文件占用显示待重试，不强制覆盖。
- 回写先生成带版本的备份，再在目标目录创建临时文件，验证后原子替换；校验成功才标记回写完成。被应用锁定时保留任务。若占用检测不可靠，先限制纳管表的直接编辑，不能承诺任何软件打开状态下都能安全写入。
- 发生“文件已替换但任务状态尚未更新”的中断时，通过回写任务中的目标文件指纹和记录映射认定是否已完成，避免重复写入。
- Excel 行号仅作当前定位。记录绑定内部 ID、来源单元格、版本及内容特征；用户插行、排序或手工改数后不能按旧行号盲写。
- 已提交记录需要更正时生成修订，保留旧值、理由、人员和时间。同步成功后才对外声称原表更新成功；同步失败仍能从数据库恢复。
- 网盘同步产生的跨设备覆盖不能由平台内的锁解决。正式使用应指定一个回写节点，纳管文件由其独占写入；其他电脑的 Excel 编辑和网盘双向写入需限制，必要时把工作文件放到受控共享目录，网盘仅作备份。

部署时服务账号必须能访问实际目标路径。桌面快捷方式只用于首次发现文件，不作为后台长期路由；本次不改变现有快捷方式。

## 5. GitHub 选型结论

调研日期：2026-10-09。项目功能来自公开说明和相关文件；本次未部署或运行这些系统。详细证据见 [GitHub 项目调研](GitHub项目调研-2026-10-09.md)。

| 项目 | 对当前需求的价值 | 采用建议 |
| --- | --- | --- |
| [SENAITE](https://github.com/senaite/senaite.core)，及 [IMPRESS](https://github.com/senaite/senaite.impress) | 最接近检测型 LIMS；可参考样品、检测记录、验证和报告模板的组织 | 优先参考业务；不作为默认新项目代码底座。检查到的 2.x 安装文档仍要求 Python 2.7，迁移文档亦需核实；原表回写仍需开发 |
| [Frappe Framework](https://github.com/frappe/frappe) | 内置角色权限、表单、管理后台、API 和报表构建，MIT 许可 | 可作为第二技术路线；若团队已有 Frappe/ERPNext 经验，优先考虑。计算与 Excel 回写仍需自定义应用 |
| [eLabFTW](https://github.com/elabftw/elabftw) | 实验记录、试剂和资源、附件及多团队权限 | 更适合实验记录归档。现有理化算法与原表回写并非其公开说明证实的现成能力 |
| [NocoDB](https://github.com/nocodb/nocodb) | 表格化录入与数据库管理，上手快 | 可做台账原型。复杂方法、版本核定和可靠回写仍需开发；当前 Sustainable Use License 有内部使用等限制 |
| [2387452986/lims](https://github.com/2387452986/lims) | 中文检测机构完整业务流程，原始记录、复核、报告和审计说明详尽 | 看业务和页面组织；README/NOTICE 明确保留权利，不能直接拿源码二开 |
| [ChemistryLIMS](https://github.com/thomasliu2020/ChemistryLIMS) | 化学检测方向，Django 架构与项目/样品/方法等分组 | 仅辅助参考。2021 年后未见新的推送，根目录未见许可文件，直接采用依据不足 |

如果希望最快建立一套标准 LIMS，可先试用 SENAITE；但本次核心是“多人平台录入后写回指定原表”，这一适配工作绕不过去。基于当前范围，轻量 Django 平台更容易控制界面、计算方法及原文件兼容性。

## 6. 首版功能与界面

| 功能 | 首版范围 | 完成的可观察结果 |
| --- | --- | --- |
| 工作台 | 按项目显示最近检测、待回写、冲突与待核查 | 人员能快速找到当日记录和未写入文件的原因 |

| 原表回写 | 预览目标位置、追加、受控修订、状态、重试、备份 | 原 Excel 对应区域与平台一致，其他区域保持原样 |
| 历史查询 | 12 份现有工作簿登记，已映射记录跨项目/批次/日期查找 | 不需逐一打开文件定位资料；未映射页保留原件浏览入口 |

录入界面建议采用两种固定形态：批量检测用普通行表格，复杂稀释/温度修正用单记录表单。结果区同时显示输入、算法参数及写表位置。首期不引入完整在线 Excel 编辑器。

正式 PDF 报告、电子签章、设备实时采集、试剂完整库存、客户门户、合同财务与 AI 判断不进入首版，除非实验室把它们明确列为当前必需项。

## 7. 最小数据结构与技术安排

| 数据实体 | 需要保存的核心信息 |
| --- | --- |
| 项目 | 代码、名称、授权人员、可用方法与工作簿 |
| 样品/送检记录 | 内部 ID、项目、批号、实际日期、来源；批号不是唯一主键 |
| 方法版本 | 检测项、核定字段与单位、公式实现标识、输出规则、生效范围 |
| 试剂批次与标定 | 试剂、批号、标定浓度、日期、有效性、依据 |
| 检测记录 | 样品、方法版本、状态、操作者、提交时间与修订链 |
| 测定明细 | 测定序号、类型化原始数据、单次结果、单位与参数快照 |
| 工作簿与映射 | 文件路径、模板版本、工作表原名、列映射与行组规则 |
| 回写任务与记录定位 | 提交 ID、目标区域、前后指纹、状态、备份、重试与冲突信息 |
| 操作日志 | 谁在何时进行了哪种操作，重要数据的前后值和原因 |

基础账号与角色复用 Django。方法实现用少量经验证的明确计算函数，按方法选择字段；不建立任意公式脚本执行器，不直接 `eval` 上传表格中的公式。数值采用 Decimal 或经核定的数值策略，明确结果位数、舍入方式及零值/缺失值区别。

4. 两人同时提交同文件、重复提交、进程中断、目标文件占用、人工插行/排序/改值时均不丢记录、不重复追加、不盲覆盖。保存状态和回写状态准确。

6. 检测记录保留来源文件、工作表、单元格、方法版本、标定参数和操作者；历史数据不被最新参数静默改算。
7. 按实际检测日期查询，文件名月份与实际日期冲突时提示，不能仅从文件名或批号猜日期。相同批号跨项目、复测和再次送检可明确区分。
8. 项目权限在后端有效；恢复备份后数据和同步文件能核对一致。正式启用前完成一次数据库和文件恢复演练。
